Operator setup and recovery

Operator works in live and simulation modes. Its journal is separate from optional ETA, PoP and model inputs. Missing predictions do not prevent calls, conferences, issues, transport reports or notes when the journal is ready.

First use

  1. Enable OPERATOR_ENABLED=true in the deployment configuration and restart the application. Keep OPERATOR_ROOT on private, durable storage.
  2. For simulation, choose the mission and start its simulation in Missions. An explicitly configured nonproduction training instance may instead supply OPERATOR_SIMULATION_RUN_ID. Operator uses the active simulation run in preference to that fallback.
  3. Open Operator. Check the source and simulation run shown in Set up this Operator journal.
  4. Select Initialize simulation journal or Initialize live journal. This explicit action creates only a pristine current namespace. It cannot reset an existing journal or switch its source.
  5. When setup finishes, create your records normally. If the source changes during setup, recheck the source and try the appropriate current namespace.

Understand the status

Status Action
Disabled Check the deployment flag and restart. No journal is opened or initialized.
First-time initialization needed Use the explicit initialization button after checking the displayed source.
Simulation run needed Start the intended mission simulation, or use the documented training launcher with its explicit namespace.
Unavailable Check the application service, storage access and free space. Keep retained drafts open, then use Recheck store.
Recovery required, corruption or identity mismatch Preserve the database, identity marker, sidecar files and backups. Initialization is blocked. Follow offline recovery below.
Mode or run mismatch Check the active source and deployment root. Never copy a live database into a simulation namespace or edit its identity marker.
ETA or model data unavailable Inspect the advisory's source details and flight/route inputs. Continue independent Operator record workflows.

Restarts and simulation runs

When the source and run context stay the same, an application restart reopens the journal with its durable store ID and epoch. Live storage and each simulation run have separate identities. Starting another run selects that run's journal; earlier files and records remain in their original namespace. They are not merged, relabeled or erased. Keep the same run when continuing work, and export the mission package before deliberately moving to another run.

Paced replay is not exact-frame restart recovery. A stopped backend may end its active replay, and a newly started replay has a new run ID. If an explicit simulation fallback is configured, it becomes the journal context when no paced run is active. Earlier run journals remain on disk; use their exact run IDs for offline verification, backup and recovery. Do not interpret the new run's empty journal as deletion of earlier records.

Unsent drafts and uncertain saves retain their original source. A changed-source save must be reconciled; it is never automatically replayed into the new journal.

Offline administration and recovery

Stop the backend before offline maintenance. Work on the configured durable root and the exact live or simulation namespace shown by health. Preserve the whole namespace before investigating; deleting a database, marker or lock file is not first-run setup.

The existing maintenance interface is python -m app.operator, run in the backend's installed Python environment. Use check --root PATH --mode live or check --root PATH --mode simulation --run RUN_ID to verify the intended journal. The backup command uses the same root, mode and run arguments. Use the documented whole-store restore procedure and a verified backup manifest when recovery is required; do not initialize over recovery artifacts.

CLI initialize remains available for deliberate offline first setup with the same root, mode and run arguments. The normal UI initialization action discovers the current server context, so ordinary first use does not require constructing that command.
