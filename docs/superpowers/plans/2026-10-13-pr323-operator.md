# PR323 Operator Workflow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve issue 324 with batch attachment, an FL default, deliberate
optimization, durable progress, and consolidated explicit reviewed publication.

**Architecture:** Reuse immutable sources and the planning journal. One browser
mission controller serializes local writes; effective leg/environment identities
drive freshness. Batch source acceptance and final publication use short
rechecked transactions, with expensive preparation outside locks.

**Tech Stack:** Python 3.11, existing planning models/store/journal, React,
TanStack Query, TypeScript, pytest, Vitest, and Playwright.

**Spec:**
[Approved design](../specs/2026-10-13-pr323-operator-and-export-repair.md).

## Global Constraints

- [Parent constraints](2026-10-13-pr323-repairs.md) apply; keep all work on
  PR323.
- Unlabelled new AR altitudes default visibly to flight level. Honor source
  units and row overrides; no repeated import/row unit acknowledgment is
  required.
- Preserve manual locks, source versions/history, UTC/occurrence semantics,
  Starshield preference, satellite access assumptions, and explicit approval.
- Autosave/apply never publishes or activates a leg. Genuine concurrent writes
  must reject stale revisions and preserve operator work.
- At most 20 explicit real-workflow actions is the target under the retained
  counting convention, subject to documented Brian-approved safety exceptions.

## Review Focus

- Explicit ft/m labels or historical unit choices cannot become FL when a new
  default is introduced (Task 1).
- A footer-like malformed genuine AR row cannot be discarded as page furniture
  merely to remove validation errors (Task 1).
- Reversed/late preview responses and another leg's save cannot silently change
  the active draft, approvals, or computational currency (Task 2).
- Two equally plausible KMLs, an invalid upload, or a replacement cannot bind to
  an arbitrary leg or delete the previous installed source (Task 3).
- One invalid leg or an interrupted final transaction cannot install part of a
  supposedly published itinerary (Task 5).

and `src/types/planning.ts`. Test backend `test_store.py`, `test_proposals.py`,

`PlanningLegReview.test.tsx` and `ExpectedLegCards.test.tsx`.

**Interfaces:** Preserve `input_identity`/mission `expected_revision` as write
CAS gates. Add proposal/reference state `applied` and an optional
`applied_input_identity`; payload hashes and original generating revision remain
immutable. `ProposalService.status(leg, reference, revision)` reports currency
from affected inputs/environment, not a global revision change alone. Define
`PlanningMissionController` in `planning-mutations.ts`, shared per QueryClient
and mission ID; the hook acquires that instance rather than creating a new queue
for each component. It provides `currentView() -> PlanningView | null`,
`beginPreview(legId: string, inputIdentity: string) -> string`, and
`acceptPreview(token: string, result: PlanningEvaluation) -> boolean`. Mutations
read the newest committed revision immediately before their queued request. Use
this queued mutation interface:

```text
enqueueMutation<T>(
    operation: (view: PlanningView) => Promise<T>,
    committedView: (result: T) => PlanningView | null
) -> Promise<T>
```

Retire an unused controller only after owned writes settle; cancel obsolete
previews on unmount while preserving durable write outcomes in the query cache.

**Interfaces:**

```text
preview_routes(
    service, mission_id, files: list[tuple[str, bytes]], expected_revision: int
```

expected revision, attachment IDs, candidate leg IDs/reason codes, and errors.

consumes explicit `(attachment_id, leg_id, discrepancy_acknowledgments)`
assignments at one expected revision. Add POST planning
`/missions/{mission_id}/route-batch-previews` and `/route-batch-acceptances`
under the existing planning router. Existing single-route APIs remain supported.
